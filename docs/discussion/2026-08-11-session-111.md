## §5 2009h21a-q091 — 未解決だった最後の 1 件をユーザー確認で決着

S110/S111 で残していた唯一の key 不一致 (§What's Next 2 に登録) を、**ユーザーに源を提示して判断を仰ぐ**形で閉じた。
推測で公式記録を書き換えないという S111 の方針を守ったまま、判断の根拠だけを揃えて渡した。

### 提示した材料

- `pages/2009h21a/page-35.png` の 問91 部分を切り出して送付 (stem・表・選択肢が 1 枚に入る)。
- 表: 注文時刻 10:00/10:30/11:00、種別 通常/優先/通常、数 80/10/40。前日在庫 100、当日仕入なし。
- 選択肢: ア 7 / イ 10 / ウ 14 / エ 20。
- 引当計算: 100 − 80 − 10 = 10 ⇒ **イ**。優先注文を先に引当てる順序 (100 − 10 − 80) でも同じ 10。
  **ウ = 14 は表のどの数からも導けない**。

### answer_keys 側の全体ずれではないことを先に否定した

「公式解答冊子の抽出が丸ごと 1 問ずれている」なら questions.json 側を疑うべきなので、近傍を独立検算した:

| 題 | questions.json | answer_keys | |
|---|---|---|---|
| 88–90 | ウ / ウ / イ | 同 | OK |
| **91** | **イ** | **ウ** | **不一致** |
| 92 | イ | イ | OK |
| 93–94 | イ / ウ | 同 | OK |

とくに **q92 (同一ページ下半、請求処理)** を独立に解いた: 10/21 請求 250,000 以降・11/21 以前の出荷
= 20,000 + 30,000 + 40,000 = **90,000 = イ**、answer_keys と一致。
⇒ この帯域に系統的オフセットはなく、**91 は孤立した 1 セルの誤り**と確定。

### 決着

ユーザーが「10 で正しい」と確認 → `data/ip/exams/answer_keys.json` の `2009h21a.answers["91"]` を
**ウ → イ** に是正。questions.json 側 (S98 で既に イ へ是正済) と一致した。

- **交叉核対 = 2900 問中 mismatch 0**。answer_keys ↔ questions の不一致は **corpus 全体で消滅**。
- Rule B の `failures/quiz_phase1.5_S98_2009h21a-q091_answerkey_mismatch.md` は削除せず、**解決追記**のみ。

### 手で直さず script にした理由 — `answer_keys.json` は gitignored

途中で気づいた点。`.gitignore` の `/data/ip/*` により **`data/ip/exams/answer_keys.json` は untracked**
(著作権・容量のため raw exams 系はローカル保持)。一方 `data/ip/quiz/questions.json` は tracked。
つまり**手で直すと git から見えず、clone し直し / 再抽出で黙って消える**。

→ S110 の `quiz-keyfix-S110.mjs` と同じ流儀で、**tracked な再実行可能スクリプト**を是正の記録とした:
`scripts/answerkey-fix-S111-2009h21a-q091.mjs`。

- 冪等 (既に イ なら skip)、**期待値ガード付き** (ウ 以外を見つけたら abort — 実際に エ を仕込んで abort を確認)
- 実行後に **answer_keys ↔ questions 交叉核対を自走**し、mismatch があれば exit 1
- 検証: 手の編集を一旦 ウ へ戻して script 単体で再現 → `1 edit / 2900 comparisons / 0 mismatches`、
  2 回目は `0 edit`

**questions.json / question_bank.json は不変** (既に イ)。よって corpus rebuild も不要、アプリ側影響ゼロ。

### 教訓

**「源から答えは出るが公式記録と食い違う」は、推測で上書きせずユーザー判断に上げるのが正解だった。**
S111 §2 の 2010h22a-q091 は公式解答の裏づけが取れたので独立導出で確定できたが、本件は裏づけが無かった。
両者を同じ「key 不一致」として機械的に処理していたら、片方は根拠不足のまま公式記録を書き換えていた。
**不一致の種類ではなく、裏づけの有無で処理を分ける。**
